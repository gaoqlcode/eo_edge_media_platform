## 2. 概念详解

### 2.1 拓扑

```text
客户端/边端
   │
   ├─ device_service   :8101  设备注册/心跳
   ├─ session_service  :8102  会话起停
   ├─ media_indexer    :8103  资产/回放索引
   ├─ alarm_service    :8104  告警
   └─ control_bff      :8105  登录 JWT + 仪表盘聚合
         │
         └─ httpx → 下游（带 X-API-Key）

edge_agent → gateway TCP:9100 / HTTP preview:9101
media_worker ← RabbitMQ emp.events
```

可选 Traefik 作统一入口（Compose）。

### 2.2 为何拆服务

- 独立扩缩、故障隔离、技术栈边界清晰  
- 代价：运维与分布式一致性更难 → 用迁移、审计、幂等补齐  

### 2.3 BFF

Backend for Frontend：给 UI/控制端一个聚合 API，避免前端直连五个服务。  
本仓：`/api/bff/dashboard`、`/api/bff/login`、`/api/bff/me`。

### 2.4 鉴权分层

| 调用方 | 方式 | role |
|--------|------|------|
| 运维脚本/服务间 | X-API-Key | service |
| 边端 | X-Device-Token | device |
| 人 | Bearer JWT | admin/operator |

RBAC 例：创建设备仅 `admin|service`（`require_roles`）。

### 2.5 可观测最小集

每个服务：`/health`、`/metrics`、日志带 `trace=`。

## 6. 自测题

1. BFF 聚合失败时本仓如何表现（看 dashboard errors 字段）？  
2. device 角色能否调用「创建设备」？为什么？  
3. 心跳为何常常不加 JWT？  

答案：1）errors 数组记录源错误；2）不能，RBAC 仅 admin/service；3）高频+设备凭证/网络隔离，本仓仍开放可后续收紧。
